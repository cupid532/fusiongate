# FusionGate V2.43 P1 Remediation Design

## Goal

Correct the confirmed P1 data-integrity and task-state bugs, remove avoidable SQLite contention from route resolution, and make the React console part of the reproducible release build without reducing existing routing or key capabilities.

## Scope

1. Aggregate usage heatmap cells by public model and date so all upstream routes contribute to one displayed cell.
2. Preserve full dates in the React heatmap and address cells by row and column index.
3. Make quality-detector job reads and state writes return errors; a persistence failure must never produce `completed`.
4. Move provider-key reads to the reader pool and load eligible keys for all route candidates in one query per resolution.
5. Build the React console in CI and in the production Docker image before compiling the Go embed.
6. Increment `fusiongate.Version` from `V2.42` to `V2.43` and document the change.

## Architecture

### Usage heatmap

The API remains a public-model-by-day heatmap. SQL groups by `public_model` and UTC date only. Because one cell can contain multiple upstream models, `upstream_model` is empty for mixed cells and retains the single upstream name only when every ledger row in the aggregate has the same upstream model. Existing JSON fields remain compatible.

The React `Heatmap` callback receives row and column indices in addition to labels and value. `Usage` uses those indices to access the exact cell. Display labels use `MM-DD`; tooltip content uses the cell's full `YYYY-MM-DD` date.

### Quality-detector jobs

Every database operation that controls a job or item state returns an error. The runner uses a small job-level failure helper to log a sanitized error and persist `failed` when possible. Item loading stops on scan or row iteration errors instead of silently skipping rows. Cancellation remains distinct from persistence failure.

### Route-key loading

Route rows continue to come from `a.reader()`. After route candidates are known, API-key candidates are loaded through one reader-pool query covering all initialized API-key providers and required upstream models. Selection still enforces per-key model inventory, default-model inheritance, enabled state, sort order, and per-key egress. Legacy uninitialized credentials continue to decrypt directly. No plaintext credential is cached beyond the request.

### Frontend release build

A Node builder stage runs `npm ci` and `npm run build`. The Go builder receives the generated `web/dist` as `internal/fusiongate/ui` before `go build`. CI independently runs frontend lint, tests, and build. The committed embed remains available for local Go-only development, while production images always use freshly generated assets.

## Error handling

- Heatmap query and scan failures continue to return HTTP database errors.
- Quality job persistence failures are logged with job ID and sanitized details; jobs never transition to `completed` after a failed load or write.
- A provider-key batch query failure makes route resolution fail rather than silently dropping every API-key route.
- Frontend build failures stop CI and image publication.

## Compatibility constraints

- Keep dynamic Provider, route, Key, model-permission, egress-node, failover, and quality-detector behavior.
- Do not add plaintext credential caches.
- Keep existing API response field names.
- Keep the sidebar version sourced from `fusiongate.Version`.
- Do not modify production deployment or production data during implementation.

## Verification

- Focused Go tests reproduce each backend defect before its fix.
- Vitest covers duplicate day-of-month columns and exact tooltip cell selection.
- Existing `go test ./...`, `go vet ./...`, and `go test -race ./...` pass.
- `npm ci`, frontend lint, tests, build, and production dependency audit pass.
- Docker image builds with generated React assets and embedded UI tests pass.
